# 2026-10-22 Next.js 보안 패치

## 변경과 근거

- 기준: `main` / `cddbae828313804b075f13d39aa256883d308bc5`. 별도 clean clone에서 수정하고, 원본 커밋의 detached worktree와 frozen lockfile로 비교했다.
- 공식 공지: https://nextjs.org/blog/nextjs-security-update-october-14-2026
- Cache Components typed-array RCE, 이미지 최적화 upstream RCE, Server Actions DoS의 수정 최소 버전은 16.4.1이다. npm registry와 공식 release에서 확인한 현재 16.x 안정 패치 16.4.2를 적용했다: https://github.com/vercel/next.js/releases/tag/v16.4.2
- `next`, `@next/bundle-analyzer`: 16.3.8 → 16.4.2. 전이 `@next/env`, 플랫폼별 SWC, Sentry peer reference도 동기화했다.
- `eslint-config-next` 및 전이 plugin: 15.5.20 → 15.5.28. 기존 FlatCompat/ESLint 9 호환 구조를 유지하고 #186의 native flat config 마이그레이션은 섞지 않았다.
- React/React DOM 19.2.7, Next 의존 경로의 sharp 0.35.5 유지. 실제 설치 경로에서도 버전을 확인했다.
- Node 24.12.0 / pnpm 10.34.7. lockfile에는 pnpm libc/deprecation 메타데이터 정규화와 TypeScript ESLint의 semver 참조 재해석도 포함된다.
- 애플리케이션 코드, 테스트, lint 규칙, build 설정은 변경하지 않았다.

## 최초 실패의 원인 분리

- 첫 테스트는 sandbox 임시 캐시 rename `EPERM`으로 93개 파일 수집 실패/실제 실행 0건이었다. 정상 권한의 단일 worker 전체 실행으로 최종 통과했다.
- 병렬 검사는 중도 종료했지만, 순차 verbose 실행은 완료 로그가 지속 증가하며 최종 통과했다. 전체 시간 중 import 약 289초, jsdom 환경 약 234초, assertion 약 20.5초였다. 지연을 assertion 실패로 분류하지 않는다.
- 최초 Turbopack loader 연결 실패는 이전 sandbox 산출물을 보존 이동하고 깨끗한 `.next`에서 단독 실행하자 사라졌다. 기준/패치 모두 동일 조건에서 통과하여 버전 회귀로 재현되지 않았다.
- Webpack의 추가 생성 타입이 남아 있으면 `tsc`도 실패한다. 깨끗한 기본 Turbopack 산출물에서는 양 버전 모두 통과하므로 build 경로의 생성 파일을 혼합하지 않는다.
- Webpack의 기존 오류 6개: `admin/events/[id]/edit/page.tsx` EventForm, `admin/events/page.tsx` FiltersBar, `admin/notifications/page.tsx` StatsBlock, `admin/profile-change-requests/page.tsx` RowActions, `admin/support/page.tsx` SupportFilters, `board/layout.tsx` isPublicBoardPath. 양 버전의 오류 목록이 정확히 일치한다.
- 이 기존 문제의 수정은 route 보조 export를 별도 모듈로 옮기고 관련 테스트 import를 조정하는 범위다. 보안 의존성 패치에 UI 구조 변경을 섞지 않았다.

## 한계와 후속 배포 준비

- 코드에서 `use cache`, `use server`, `cacheComponents`는 발견되지 않았다. 이는 운영 버전이나 비취약성의 증거가 아니다.
- Windows 로컬 검증이다. 운영 glibc Linux 이미지, 실제 배포 버전, real API/DB E2E 및 API 전용 검사는 미검증이다.
- Linux CI의 정식 lint/guards 및 필수 gate를 확인해야 한다. 기존 Webpack export 오류, import cycle 검사 성능과 Windows guard 제외 경로는 별도 범위로 다룬다.
- 실제 배포 이미지의 Next/sharp 버전과 rollback 대상을 확인한 뒤 별도 배포 승인을 받아야 한다.
- 로컬 검증 이후 GitHub push, 초안 PR 생성, CI 확인은 별도 사용자 승인을 받았다. merge, auto-merge, 운영 배포, 기존 서비스 재시작은 승인 범위에 포함되지 않는다. 유료 Security Cloud 및 라이브 공격 테스트는 수행하지 않았다.
